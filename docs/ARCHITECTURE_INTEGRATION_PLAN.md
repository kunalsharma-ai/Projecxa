# Architecture and integration plan

## Shape

One repository, two apps, one database. The API is a modular monolith; modules are split out only when scale or isolation requires it.

```
apps/
  api/   NestJS 11 + Prisma 6 + PostgreSQL 16   → http://localhost:4000
  web/   Next.js 15 (App Router) + Tailwind     → http://localhost:3000
docs/
```

### API modules (`apps/api/src`)

| Module | Responsibility |
|---|---|
| `auth` | JWT in an httpOnly cookie (or `Authorization: Bearer`), global guard, role decorators. Staff roles by default; portal roles must be granted per endpoint. |
| `clients`, `vendors`, `users` | Master records, tenant scoped. Secrets (client S2S, vendor callback) are only readable by admins. |
| `projects` | Master project → countries → quota cells → vendor allocations. Multi-country merge of shared defaults and overrides. |
| `redirects` | Pure resolver (`redirect-resolver.ts`), single engine (`redirect-engine.ts`) used by live traffic and the QA studio, versioned policy service. |
| `survey` | Public respondent endpoints: `/s/:code` entry, `/r/:status` outcome, `/end/:status`, signed `/api/v1/s2s/outcome`. |
| `callbacks` | Transactional outbox for server-to-server callbacks, worker with backoff, replay endpoint. |
| `dashboard` | Dashboard numbers, organization settings, complete approval. |
| `audit` | Append-only audit events. |

### Data model

`Organization → Client → Project → ProjectCountry → (QuotaCell, VendorAllocation) → RespondentSession → (RespondentEvent, RedirectExecution)`, plus `RedirectPolicyVersion`, `CallbackDelivery`, `AuditEvent`. See `apps/api/prisma/schema.prisma`.

Design rules:
- Every tenant-owned row carries `organizationId` or hangs off a row that does; every query filters by the caller's tenant.
- Human IDs (`PRX10001`, `WO9001`) come from per-tenant sequences; prefixes are configurable so legacy `FRP…`/`FR…` numbering can be kept when data is migrated.
- Redirect configuration is stored as immutable versions. Sessions keep a reference to the version they started under, so changes and rollbacks never rewrite history.
- Respondent outcomes are recorded once, guarded by a conditional update (`WHERE status = 'STARTED'`) and a unique event key. Completes increment country and vendor counters with conditional SQL (`completes < target`), so concurrent traffic cannot over-allocate.
- A browser redirect never makes a complete billable: completes start as `PENDING` approval; S2S confirmation sets `outcomeVerified`.

### Redirect resolution

Precedence (most specific first; the security policy always wins):

1. Mandatory security policy: https (http only outside production), allowlisted domains (organization + that vendor's own), no credentials, no loops into SampTrek links
2. Project rule for vendor + country
3. Project rule for vendor
4. Project rule for country
5. Project rule
6. Client redirect template
7. Organization default

Two enabled rules at the same level for the same status are a conflict: validation blocks activation, and at runtime the engine falls back rather than guessing. A disabled rule disables the status at that level instead of falling through. Fallback is the organization fallback URL if it passes the policy, else SampTrek's neutral end page.

## Integration with other Sampledge products

| Product | Owns | Contract with SampTrek (planned) |
|---|---|---|
| Bidzo | RFQs, bids, pricing | Bidzo emits `bid.won` (webhook) → SampTrek creates a draft project with `bidReference`, client, markets, LOI/IR/CPI. SampTrek never stores bid pricing workflows. |
| DealFlow | Sales pipeline | Read-only lookup of the sales owner / account; no copy of pipeline data. |
| Panel management | Panelists | SampTrek treats the Sampledge panel as a vendor: one vendor record, entry links and callbacks like any external supplier. |
| Survey programming | Questionnaires, hosting | Uses the documented client survey integration (`docs/SURVEY_INTEGRATION.md`): session token in, `/r/:status` out, optional signed S2S. |
| Supply CRM / Crew | Supplier relationships, staff | To be confirmed with the product owner; avoid duplicating vendor master data by syncing vendor IDs. |

These contracts need the other repositories' event and API shapes before they are built; nothing in milestone 1 calls another product.

## Infrastructure decisions

- **Redis**: provisioned in `docker-compose.yml` but unused in milestone 1. The callback outbox runs on Postgres with a guarded claim so it is safe with several API instances. Move to BullMQ when callback volume or scheduling needs justify it.
- **Secrets**: `.env` only; nothing secret in the web bundle. Client and vendor secrets are random 256-bit values generated by the API.
- **Respondent privacy**: the vendor's respondent ID is never sent to the client survey (an opaque token is used instead). IPs are stored only as a salted SHA-256 hash.
